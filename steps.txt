3. VERIFIER KEY CUSTODY  (READ KEYS.md BEFORE TOUCHING ANY KEY)
--------------------------------------------------------------------------------
Verifier keys are the trust model. They decide which wallets the world recognises
as real institutions. They are NOT disposable, and the habit should be right on
testnet so it is right by the time it matters.

  - Generate each one separately:  cast wallet new
  - Separate custody per verifier. Not all on one machine.
  - Import into Foundry's encrypted keystore, never into .env:
      cast wallet import edgrant-verifier-a --interactive
  - .env holds verifier ADDRESSES ONLY. Never a verifier private key.
  - Threshold >= 2 on testnet. Above 2 on mainnet.

Blast radius if `threshold` of them are compromised: an attacker can verify a
fake school and take FUTURE donations, and can grief by revoking real ones. They
CANNOT redirect an existing request — request.school is set once at creation and
no setter exists anywhere (test_disbursementDestinationIsImmutable). That
containment is why the vault has no administrative surface, and it is the reason
this is survivable rather than fatal.

The DEPLOYER key is genuinely disposable: neither contract stores msg.sender in
its constructor and there is no owner variable anywhere
(test_deployerRetainsNoPrivilegeAfterConstruction).

4. DEPLOY ALL FOUR CONTRACTS TO 968
--------------------------------------------------------------------------------
  cp .env.example .env
  # fill in: VERIFIERS (addresses, comma separated), VERIFIER_THRESHOLD,
  #          VERIFICATION_FEE_WEI
  cd contracts
  forge script script/Deploy.s.sol:Deploy --rpc-url bohr --broadcast \
    --verify --verifier blockscout

The script refuses fewer than two verifiers and refuses to guess a token address
on an unknown chain. Both refusals are deliberate: the registry and token are
IMMUTABLE in the vault, so a wrong value at deploy time is unrecoverable.

If Blockscout verification fails, retry it separately rather than redeploying:
  forge verify-contract <address> src/EducationFundingVault.sol:EducationFundingVault \
    --chain 968 --verifier blockscout \
    --verifier-url https://scan.bohr.life/api
Unverified source on a block explorer undercuts the entire "check it yourself"
argument, so treat verification as part of deploying rather than a nice-to-have.

7. LIVE END-TO-END REHEARSAL WITH KEYS HELD BY DIFFERENT PEOPLE
--------------------------------------------------------------------------------
This is the step most likely to be skipped and the one most worth doing. The
verifier flow has only ever been exercised with one person holding every key,
which is the one configuration that proves nothing about m-of-n.

  - 3 verifiers on 3 machines, 3 separate wallets
  - 1 school on its own machine
  - 2-3 contributors, at least one on a phone on mobile data

  Walk the whole path:
    school applies -> verifier A confirms -> NOTHING HAPPENS (this is the point)
    -> verifier B confirms -> verified
    school publishes a profile and attests a fee balance
    contributors approve + contribute from separate wallets
    a THIRD party calls release() — nobody involved in the request
    then, on a second request, let a deadline pass unmet and have each
    contributor withdraw their own contribution
    then revoke a verification and confirm payout becomes impossible while
    withdrawals open immediately

  Write down anything a participant had to ask you to explain. Every one of those
  is an interface defect, because the whole claim is that a supporter should not
  need documentation to understand where the money goes.

--------------------------------------------------------------------------------
THINGS NOT TO DO
--------------------------------------------------------------------------------
  - Do NOT remove the chainid != 677 guard in SeedDemo.s.sol. On testnet,
    self-approving a fictional school is how you exercise the flow. On mainnet it
    is precisely the impersonation this project exists to prevent.
  - Do NOT add an admin override, a pause, or a cancel to the vault. If a change
    appears to need one, the change is wrong (R2).
  - Do NOT unify the evidence panel and the self-asserted panel. They differ on
    purpose and the browser test asserts their computed styles differ. Profile
    content is marketing; the badge is evidence (D-10, D-21).
  - Do NOT add a countdown, a "days left" badge, or scarcity copy. Urgency is the
    fraudster's tool. The browser test greps for it (D-22).
  - Do NOT reconstruct interface state by scanning logs. eth_getLogs is
    restricted on the 677 public RPC; it will work on testnet and fail on mainnet
    (C1, D-15).
  - Do NOT let the interface fall back from one chain's addresses to another's.
  - Do NOT put a verifier private key in .env, on testnet or anywhere.
