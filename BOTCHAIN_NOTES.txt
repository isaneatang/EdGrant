  Evidence, verified live rather than taken from marketing copy:
    - web3_clientVersion -> "Geth/v1.5.13-666da20c-20260818/linux-amd64/go1.26.6"

    - BSC system contracts live at 0x...1000-0x...2000 (saw 0x...1002 emit logs)

  Marketing positions it as "AI-native L1 for AI agents / DePIN". That framing
  is irrelevant to us. There are no AI precompiles or agent-specific opcodes in
  the docs. We are building a normal EVM dApp on a fast, cheap BSC clone.

DISCOVERY 1 - BOT CHAIN ALREADY SHIPS AN ON-CHAIN IDENTITY STACK (ERC-3643)
--------------------------------------------------------------------------------

This is the biggest finding of the session and it lands directly on top of
"Contract One: Identity Verification Registry" from the essay.

BOT Chain has deployed and verified a full T-REX / ERC-3643 suite plus the
ONCHAINID identity infrastructure ("Project RWA"), on BOTH 968 and 677:

  ONCHAINID Gateway  - self-service; anyone calls deployIdentityForWallet(wallet)
                       to mint themselves an on-chain identity contract
  IdFactory          - wallet -> identity contract mapping
  ClaimIssuer        - platform-run signer that issues signed eligibility claims
  TrustedIssuersReg. - which issuers an asset recognises, per claim topic
  ClaimTopicsReg.    - which claim topics an asset requires
  IdentityRegistry   - isVerified(wallet) -> bool, the eligibility oracle
  ModularCompliance  - pluggable transfer-rule modules

  Testnet (968) shared addresses:
    ONCHAINID Gateway  0x3B0FE2CD501534cbcbD1F97ec823Da535fc0224f  (has code, OK)
    IdFactory          0xb4E03AB303f4c42dbced87b65e1d9f5788EAb369
    ClaimIssuer        0x67EC753196D6Cd1B65a29b6ff9c1bE41E554a5a7
    TREXGateway        0x82e1Fa8022BA1dcFC05061E0A1CE828C189108A9
  Mainnet (677) shared addresses:
    ONCHAINID Gateway  0xa6B4E53128915E0f980DD455De9F70B6Dc61E1ee
    IdFactory          0x124ED389600870D1a5f86f657896Add3E623ca9e
    ClaimIssuer        0x3950eB42733b3eF6744E8788C741788CCF6c84b3

THE DECISION THIS FORCES:
  Do we build our own VerifiedEntityRegistry, or ride on ONCHAINID?

RECOMMENDATION: build our own standalone registry. Reasons:

  a) SEMANTIC MISMATCH. Their stack answers "is this wallet a KYC'd investor
     permitted to hold security token X". We need to answer "is this wallet a
     real school, and here is the public proof anyone can re-check". Their live
     claim topic is literally KYC_APPROVED and their live compliance module is a
     country allowlist hardcoded to China (156) and Singapore (702). Wrong shape.

  b) TRUST DELEGATION. Their ClaimIssuer signing key is held by the BOT Chain
     team. Riding on it means our entire trust model is downstream of their key
     management and their review process. The essay's whole argument is that we
     own and are transparent about the one centralised component. We cannot be
     honest about a process we do not run.

  c) THE ESSAY EXPLICITLY WANTS IT REUSABLE AND STANDALONE. It is the project's
     actual novelty. Outsourcing it outsources the thesis.

  d) Their own docs warn the mainnet suite is a "technical capability demo",
     the compliance module is UNAUDITED, and it "must not directly carry real
     assets". Not a foundation to build on.

BUT WE SHOULD STEAL THEIR PATTERNS - they are ERC-3643 patterns and they are good:
  - Split Owner (governance/upgrade) from Agent (routine ops). Never one key.
  - Multisig the Owner. Their own docs recommend Safe + delayed execution.
  - Revocation is first-class, not bolted on. Matches the essay exactly.
  - Keep plaintext PII off-chain; store only the verifiable conclusion + a URI
    pointer. This is EXACTLY the essay's privacy stance, already validated by a
    regulated-asset framework. Strong corroboration that our design is sane.
  - Separate the "management key" from the "claim signing key".

OPTIONAL BRIDGE (nice-to-have, later): expose a view on our registry that also
reports whether the school wallet happens to hold a valid ONCHAINID. Additive
signal, never a dependency. Do not gate anything on it.

DISCOVERY 2 - USDT IS AVAILABLE ON TESTNET, AND WE SHOULD PROBABLY USE IT
--------------------------------------------------------------------------------

  USDT testnet (968)   0x75edC9335175Fc0552D51D48439F229c10420fe3
  USDT mainnet (677)   0xaBabc7Ddc03e501d190C676BF3d92ef0e6e87a3C
  Decimals: 6  (verified live: symbol() -> "USDT", decimals() -> 6)
  The faucet dispenses test USDT as well as tBOT.

WHY THIS MATTERS A LOT:
  School fees are fiat-denominated debts. "Student owes 450" means 450 dollars,
  not 450 BOT. If a request is denominated in native BOT and BOT moves 30%
  between creation and deadline, the goal amount becomes meaningless - either
  the school is underpaid or contributors overpay. The attestation "this school
  says this student owes this amount" is only coherent in a stable unit.

  => Denominate goals in USDT (6dp). This is a correctness issue, not a
     preference.

THE COST OF THIS CHOICE (be honest about it):
  ERC-20 contribution = approve() then contribute() = 2 transactions.
  Native BOT contribution = 1 transaction, payable, simpler contract, no
  transfer-return-value edge cases, no reentrancy surface on refund.

  Mitigations available on this chain:
    - Permit2 IS deployed. Testnet 0xaE85b2bc7578F8Ca9217900a2D548151F96447de,
      mainnet 0x8366170f09a04f715a13549D616a06aED16Db7c3. Gives sign-once
      approvals, collapsing the UX back toward one action.
    - Check whether this USDT implements EIP-2612 permit(). NOT YET VERIFIED.
      If it does, we can skip Permit2 entirely for the simple path.

  PROPOSED: write the vault token-agnostic (immutable IERC20 set at deploy)
  rather than hardcoding USDT or hardcoding native. Deploy the testnet instance
  against test USDT. Keep native-BOT support out of v1 - mixing native and
  ERC-20 accounting in one vault doubles the refund logic and doubles the audit
  surface for no real gain.

  CAUTION: real Tether on Ethereum famously does not return a bool from
  transfer(). Unknown whether this bridged USDT copies that quirk. Use
  SafeERC20 unconditionally. Assume nothing.

DISCOVERY 3 - GASLESS DONATIONS ARE POSSIBLE (EOA PAYMASTER)
--------------------------------------------------------------------------------

BOT Chain inherits BSC's EOA-based paymaster. Note carefully: this is NOT
ERC-4337. No smart accounts, no EntryPoint, no UserOperations.

How it actually works:
  1. Wallet asks the paymaster JSON-RPC: pm_isSponsorable({from,to,value,data,gas})
  2. If sponsorable -> wallet signs the tx with gasPrice = 0
  3. Wallet submits to the paymaster's eth_sendRawTransaction
  4. Paymaster bundles the zero-gas user tx with its own fee-paying tx and ships
     the bundle to MEV builders; the bundle executes atomically
  Provider named in docs: NodeReal "MegaFuel".

WHY IT MATTERS FOR EDGRANT:
  Our two hardest adoption problems are both gas problems.
    - A school registrar will not buy BOT to issue a fee attestation.
    - A donor who wants to give $20 will not first acquire a gas token.
  Sponsoring exactly two call paths - createRequest by a verified school, and
  contribute by anyone - removes the biggest onboarding cliff in the product.

  It also composes beautifully with the trust model: we can sponsor gas WITHOUT
  ever touching the donated funds. The paymaster pays the validator, not us, and
  the money still goes wallet -> vault -> school. No custody is introduced.

STATUS: PHASE 2. Do not design v1 around it.
  UNVERIFIED: whether a paymaster endpoint actually exists on testnet 968, and
  whether we can get a sponsor policy provisioned. Must confirm before promising
  gasless anything in the UI.
  Also note: gas here is trivially cheap (20 gwei on a 0.7s-block chain), so the
  win is purely "user has zero BOT", not cost. That is still the whole ballgame
  for a first-time donor.

DISCOVERY 4 - eth_getLogs IS RESTRICTED ON THE PUBLIC MAINNET RPC
--------------------------------------------------------------------------------

The docs state plainly: "eth_getLogs is disabled on below Mainnet endpoints."

Probed it live. A single-block query against https://rpc.botchain.ai DID return
logs, so it is not a hard block - it is almost certainly range-limited or
rate-limited. Either way, treating the public mainnet RPC as a queryable log
source is a trap.

This is an ARCHITECTURE constraint, not a footnote. The essay says "the entire
history of any request is publicly reconstructible" - that promise is delivered
by event indexing. If we build the frontend to reconstruct state by scanning
logs from block 0, it will work beautifully on testnet and fall over on mainnet.

MITIGATIONS, in order of preference:
  1. Make the contracts answer directly. Maintain enumerable on-chain state
     (request IDs array, per-school request list, per-contributor list) with
     paginated view functions. Then the UI needs zero log scanning for its core
     flows. Costs some gas on write; gas is nearly free here. Strongly favoured.
  2. Run our own indexer. Docs name TheGraph and Covalent.
  3. WebSocket subscriptions for live updates. wss://rpc.bohr.life probe was
     inconclusive (got 200 not a 101 upgrade) - UNVERIFIED, needs a real ws client.

  => DESIGN RULE: events are for auditability and indexers. The dApp must remain
     fully functional using only eth_call against view functions.

DESIGN POSITIONS CARRIED OVER FROM THE ESSAY (non-negotiable, restated so we do
not quietly drift away from them while writing code)
--------------------------------------------------------------------------------
  - Money NEVER routes through the student. Vault -> verified school wallet only.
  - Disbursement destination is read from the registry at release time, and is
    displayed in the UI on the contribution screen, before the donor signs.
  - No admin override. No pause. No deployer escape hatch on the vault. If we
    find ourselves adding one "just in case", we have broken the thesis.
  - Refunds are individually pull-based. No pooled refund. No sweeping of
    unclaimed funds anywhere, ever.
  - Verification is proof-of-control, not subjective review. The stored proof
    URI must be publicly re-checkable by any skeptical donor in one click.
  - Student PII stays off-chain. On-chain student reference is a school-internal
    opaque identifier. Pseudonym + statement are strictly optional.
  - Tone: calm and serious. No countdown-timer urgency theatre. Urgency is the
    fraudster's tool and we are the anti-fraud product.

--------------------------------------------------------------------------------
DECISIONS MADE WHILE BUILDING (each of these is a place the essay did not
specify an answer, so the reasoning is recorded rather than just the outcome)
--------------------------------------------------------------------------------

D-01  DENOMINATE IN USDT, NOT NATIVE BOT.  [user-confirmed]
      A fee debt is fiat-denominated. "Owes 450" means 450 dollars. If the goal
      were in BOT and BOT moved 30% before the deadline, the school is underpaid
      or the donors overpay, and the attestation stops describing anything real.
      Cost accepted: approve + contribute is two transactions.
      Vault takes an immutable IERC20 at construction rather than hardcoding
      USDT, so the same code can be deployed against a different stable unit.
      Deliberately NOT supporting native BOT in the same vault - mixing native
      and ERC-20 accounting doubles the refund logic and the audit surface.

D-02  BUILD OUR OWN REGISTRY RATHER THAN RIDING ONCHAINID.
      Reasoning in full at ENTRY 001 / DISCOVERY 1. Short version: their claim
      topic is KYC_APPROVED for securities investors, their ClaimIssuer key is
      the BOT Chain team's, their live compliance module is a China/Singapore
      country allowlist, and their own docs call the mainnet suite an unaudited
      capability demo. Wrong semantics, and it would put our trust model
      downstream of someone else's key management.
      We did adopt their good patterns: role separation, first-class revocation,
      PII off-chain with only a URI pointer on-chain.

D-03  REVOCATION MAKES A REQUEST REFUNDABLE IMMEDIATELY.
      The essay does not say what happens to in-flight requests when a school is
      revoked. Derived it from the stated philosophy - "never let the money touch
      a party who has no business holding it":
        - release() re-checks isVerified() at the moment of transfer, not just at
          creation. A revoked school cannot be paid even if fully funded.
        - refund() becomes available the instant verification is lost, without
          waiting for the deadline.
        - contribute() is blocked for a revoked school, so nobody adds to a dead
          request.
      Griefing note, stated honestly: verifiers CAN revoke to block a specific
      disbursement. That is inherent to having revocation at all. It is
      acceptable because the only thing revocation can ever do is return money to
      the people who sent it. It can never redirect funds to anyone. Revocation
      fails in the safe direction, which is the property we actually need.

D-04  THE REGISTRY IS SELF-GOVERNING. THERE IS NO OWNER.
      The essay demands a multisig "so that no individual can unilaterally grant
      or revoke institutional identity". An `owner` who can swap the verifier set
      would be a backdoor around exactly that - the owner could install itself as
      sole verifier. So: no owner exists. Verifier-set changes require the same
      m-of-n as approvals.
      Implemented as a generic operation-hash confirmation pattern:
        approve  -> keccak(APPROVE, requestId)      unique via request status
        reject   -> keccak(REJECT, requestId)
        revoke   -> keccak(REVOKE, account, entityEpoch[account])
        governance -> keccak(op, args, governanceNonce)
      entityEpoch exists so an approve->revoke->approve->revoke cycle cannot
      replay a stale revoke hash. Tested: test_reapplyAfterRevocationSucceeds.
      governanceNonce means only ONE governance op can be in flight at a time.
      Accepted limitation; verifiers coordinate off-chain like any multisig.
      removeVerifier() takes newThreshold in the SAME call so the set can never
      be left with threshold > verifierCount, which would deadlock the registry
      permanently. Tested: test_removeVerifierCannotDeadlockThreshold.

D-05  release() IS A SEPARATE PERMISSIONLESS CALL, NOT AUTO-TRIGGERED.
      The essay says "when the goal is met, the contract sends the funds". Doing
      that inside the goal-completing contribute() would (a) charge one unlucky
      donor for everyone else's disbursement, (b) put an external call inside
      contribute, and (c) let a school address that reverts on receipt break
      contributions for everybody. Instead: emit GoalReached, and let anyone
      call release(). Same outcome, no hostage-taking. Documented in the code.

D-06  OVERFUNDING REVERTS RATHER THAN BEING TRIMMED.
      Silently taking less than a donor asked for is surprising and erodes the
      legibility the essay demands. contribute() reverts with
      ExceedsRemaining(remaining) and the UI offers "fill the remainder".

D-07  THE SCHOOL WRITES THE STUDENT'S OPTIONAL CONTEXT, NOT THE STUDENT.
      The essay says the student "may optionally attach" a pseudonym and
      statement. Letting the student write it directly would require the student
      to hold a wallet and pay gas, which is a real adoption barrier and forces
      a student address on-chain - worse for the privacy goals. So the school
      submits context it collected off-chain, via setContext(), guarded to the
      school and unable to affect where money goes. Students never need a wallet.
      Flag: this is a deviation from a literal reading of the essay. Revisit if
      student-authored context turns out to matter.

D-08  ON-CHAIN ENUMERATION IS MANDATORY, NOT AN OPTIMISATION.
      Direct consequence of ENTRY 001 / DISCOVERY 4 (eth_getLogs restricted on
      the public mainnet RPC). Both contracts keep enumerable arrays with
      paginated getters. requestSummary() returns everything a contribution
      screen needs in ONE call - including disbursementDestination and the
      school's proofURI, so the UI can show the donor where the money goes and
      link the verified badge to re-checkable evidence before they sign.
      Gas is ~free here, so the write-side cost is irrelevant.

D-09  APPLICATION FEE IS IN NATIVE BOT, NOT USDT.
      Keeps the registry free of any ERC-20 dependency, which matters because the
      essay wants it reusable by other projects. Also avoids an approve step on
      the very first interaction a school ever has with us.
      Fee is refundable in full via withdrawRequest() ONLY while zero verifiers
      have confirmed. Once review has begun the fee is consumed either way,
      including on rejection - otherwise impersonators get free retries and the
      deterrent evaporates. Tested both paths.

USER DECISIONS THIS ROUND
  Q: what does "offer the school fees available to mint" mean?
  A: publish fundable fee requests. => That IS createRequest, already built.
     "Mint" here means the school issues/creates a fundable fee item, NOT an

       - a reusable fee catalog / template system
       - tokenising the fee debt as a transferable claim (would have changed the
         trust model substantially - closer to the ERC-3643 RWA territory)

  Q: where should profile content live?
  A: FULLY ON-CHAIN. Not an IPFS/JSON pointer.
     => New contract SchoolProfile.sol stores profile fields and posts as
        contract state. Honest caveat recorded in the contract: image BYTES
        obviously cannot live on-chain, so logoURI/bannerURI are still URIs.
        The profile FIELDS are on-chain; the images they point at are not.
     => Gas is near-free on this chain (20 gwei, 0.7s blocks), so the usual
        objection to on-chain content does not really apply here.

D-10  PROFILE CONTENT IS SELF-ASSERTED AND MUST NEVER BE RENDERED AS EVIDENCE.
      This is the single most important thing about SchoolProfile and it is a
      trust-model issue, not a styling preference.
      The ONLY verified facts in this system are in VerifiedEntityRegistry: that
      an address is controlled by the named institution, plus the proofURI.
      Everything a school types into its profile - name, description, logo,
      admissions posts - is checked by nobody.
      If the UI renders profile text with the same visual authority as the
      verified badge, it hands impersonators exactly the credibility this whole
      project exists to deny them. A fraudster's profile would look identical to
      a real one.
      => PROFILE CONTENT IS MARKETING. THE BADGE IS EVIDENCE. SHOW THEM
         DIFFERENTLY. Written into the contract docs so it survives a rewrite.

D-11  WRITE REQUIRES VERIFICATION; READ NEVER DOES.
      A revoked school cannot keep publishing (onlyVerified on every write), but
      its existing profile stays readable. Deliberate: the interface needs to
      show what was claimed NEXT TO the fact that the badge is gone. Deleting
      the profile on revocation would destroy exactly the evidence a donor
      wants after something goes wrong.

D-12  HIDING A POST IS NOT DELETING IT, AND WE SAY SO.
      setPostVisibility(id,false) removes a post from the public feed. It does
      not and cannot erase it - public chain, still in state and history. The
      contract documents this rather than shipping a delete button that lies.

D-13  NEW STATELESS LENS CONTRACT (EdGrantLens.sol).
      Direct consequence of D-08 / constraint C1 (eth_getLogs restricted on the
      public mainnet RPC). Two reasons it earns its place:
        a) A school profile page needs profile + posts + open requests +
           aggregate stats. Without a lens that is dozens of round trips.
           schoolPage() answers it in ONE eth_call.
        b) Stateless and value-free means it can be REDEPLOYED FREELY as the UI
           evolves, without migrating state or touching contracts that hold
           money or grant identity. Presentation churn must never require a
           value migration.
      SchoolStats.totalDisbursed is the field that matters most for trust:
      money that ACTUALLY REACHED the institution, derived from chain state,
      unfakeable. "$8,400 delivered across 12 students" is a stronger and more
      honest signal than anything a school could write about itself.

D-14  DUMMY-SCHOOL SEEDING IS SCRIPTED, AND HARD-BLOCKED ON MAINNET.
      script/SeedDemo.s.sol runs the whole path: school applies -> 2 verifiers
      approve -> profile + 2 posts published -> 3 fee requests created -> donor
      partially funds one and fully funds another.
      On testnet, self-approving your own fictional school is simply how you
      exercise the flow; you hold every key and nothing represents a real
      institution. On MAINNET the identical action is precisely the
      impersonation this project exists to prevent, so the script requires
      block.chainid != 677. DO NOT REMOVE THAT GUARD.
      One request is deliberately left with NO student context, to keep proving
      the mechanism works fully when a student shares nothing at all.

BUILT: web/ - Next.js 16 App Router, React 19, wagmi 3, viem 2, Tailwind 4, TS.
All seven planned pages, plus /portfolio which was not in the original plan and
turned out to be necessary (see D-17).

STATE: 49 unit tests, 12 integration tests against a live chain, 58 browser
checks, all passing. Typecheck, lint, and a production build all clean.

D-15  THE READ PATH IS ASSERTED, NOT ASSUMED.
      C1 said the dApp must work from view calls alone. That is a promise nobody
      can keep by intention alone - somebody eventually adds a log query because
      it is convenient, it works perfectly on 968, and it fails on 677.
      => The integration test wraps the viem transport in a counting proxy,
         exercises every screen, and asserts eth_getLogs == 0. Exercising all
         seven pages produced 28 eth_call and NOTHING ELSE. C1 is now a
         regression test rather than a design intention.

D-16  DERIVED STATE PREFERS THE CONTRACT'S CLOCK OVER THE BROWSER'S.
      deriveRequestState() takes the vault's own `refundable` flag and recovers
      the deadline verdict from it, rather than comparing a deadline to
      Date.now(). block.timestamp is the only clock that decides whether a call
      succeeds. It can differ from a visitor's through ordinary skew, a timezone
      bug, or a local chain whose time has been advanced for testing.
      This was not theoretical: the portfolio page shipped with the naive version
      and the browser test caught it filing a genuinely withdrawable balance
      under "in progress" - on the one page whose entire purpose is getting money
      back. Both the unit test and the browser test now pin it.
      Deadline BOUNDS in the school console come from useChainTime() (the latest
      block timestamp) for the same reason: the vault validates against
      block.timestamp, so offering a date the vault will reject is a bug.

D-17  A CONTRIBUTOR PAGE WAS NOT OPTIONAL.
      Not in the original page list. R3 says refunds are individual and
      pull-based, nothing is ever swept, and no administrator distributes
      anything. That property is only HONEST if a contributor can find what they
      are owed without help. Read from vault.requestsByContributor(you), which
      exists on-chain precisely because of C1. Withdrawable balances are pulled
      to the top and totalled.

D-18  STUDENT REFERENCES ARE HASHED CLIENT-SIDE, AND THAT CREATED A REAL PROBLEM
      WE HAD TO SOLVE RATHER THAN IGNORE.
      Consistent with SeedDemo.s.sol: keccak256 of a school-internal identifier
      goes on-chain, never the identifier. Even a bare enrolment number is a
      re-identification vector once it is public and permanent (R5). The hash is
      shown before signing so nothing is concealed.
      The cost: a registrar cannot read a request back and recall which student
      it belongs to. Left there, schools would have quietly started putting
      readable identifiers - or names - in the pseudonym field instead.
      => The school console has a REFERENCE MATCHER. Type a candidate reference,
         it is hashed locally, and the matching request is highlighted. Nothing
         leaves the browser. Privacy that is workable is privacy that survives.

D-19  APPROVAL IS FOR THE EXACT AMOUNT, NEVER UNLIMITED.
      C3 means approve + contribute is genuinely two transactions. Shown as two
      numbered steps rather than hidden behind one button that opens two prompts.
      The approval is for exactly the amount typed. More friction on a second
      contribution; considerably less standing authority granted to a contract.
      For a product whose argument is "grant no more power than the mechanism
      needs", unlimited-by-default would be incoherent. The panel states the
      policy whether or not an approval is currently outstanding, because it is a
      standing commitment and not a transient hint.

D-20  UNTRUSTED URIs GO THROUGH AN ALLOWLIST, NOT A BLOCKLIST.
      proofURI, logoURI, bannerURI, website are all supplied by the entity being
      displayed, and then rendered as something a donor is invited to click. Only
      http(s) and ipfs:// become live links; everything else renders as inert
      text WITH THE REASON, because a hostile proof URI is itself a finding a
      donor should see rather than something to silently drop. Unit tested
      against javascript:, data:, vbscript:, file:, blob:, about:, chrome:, and
      a malformed-ipfs traversal.
      Images are plain <img> with an onError fallback, never next/image: keeping
      the fetch in the visitor's browser means a school cannot make our server
      request arbitrary URLs on its behalf.

D-21  D-10 IS ENFORCED BY TEST, NOT BY COMMENT.
      "Profile content is marketing, the badge is evidence, show them
      differently" is the kind of rule a future redesign undoes while tidying up
      visual inconsistency. So the browser test reads COMPUTED STYLES and asserts
      the self-asserted panel is dashed, the evidence panel is not, and their
      backgrounds differ. Wording alone is not sufficient and is not what is
      checked.
      Also enforced: if a school's self-chosen display name differs from the name
      it was verified under, the interface says so next to it.

D-22  "NO URGENCY THEATRE" IS ALSO ENFORCED BY TEST.
      The browser test greps the rendered page for hh:mm:ss timers, "hurry",
      "act now", "last chance", "only N days left", and flame/alarm emoji.
      useNow() ticks once a MINUTE and is documented as display-only, which makes
      a countdown impossible to build accidentally. Deadlines render as dates.

D-23  TRANSACTIONS RETURN THE RECEIPT, NOT JUST THE HASH.
      createRequest returns the new request id, which a transaction cannot hand
      back to a caller. The naive fix - re-read requestCount and subtract one -
      races with any other school creating a request in the same block. Instead
      useTxRunner returns the mined receipt and the caller decodes RequestCreated
      out of it. That is not a log SCAN: it is the receipt we already hold, so C1
      does not apply and there is no race.

D-24  ADDRESS RESOLUTION IS ALL-OR-NOTHING PER CHAIN.
      contractsFor(chainId) returns null unless ALL FIVE addresses resolve.
      A half-configured chain is the failure mode most likely to point a
      contribution somewhere wrong. Priority: env var > chains.json > generated
      local file. There is no cross-chain fallback anywhere, and every screen has
      an explicit "not deployed on this network" state that says so.

BUGS THE BROWSER LAYER CAUGHT THAT NOTHING ELSE WOULD HAVE
  Recorded because they justify the cost of that layer, and because three of the
  four are trust-model regressions rather than cosmetic faults.
    1. approve and contribute shared one useTxRunner, so the approval succeeding
       cleared the amount field and disabled the contribute button. A donor had
       to retype the figure they had just committed to.
    2. the portfolio used browser time instead of the vault's refundable flag
       (D-16).
    3. the school page linkified proofURI but had no explicit "re-check the proof"
       affordance - the single most important action in the trust model was a
       bare URL.
    4. a dead logo URI left a torn-image glyph on an institution's page.

TOOLING NOTES, so the next person does not rediscover these
  * eslint-config-next 16 ships NATIVE flat config. The @eslint/eslintrc
    FlatCompat bridge dies with "Converting circular structure to JSON" on the
    plugin graph it produces. Import eslint-config-next/core-web-vitals and
    /typescript directly.
  * Next 16 removed the `eslint` key from next.config. Linting is a separate step.
  * next.config needs allowedDevOrigins including "127.0.0.1", or Next silently
    403s every /_next chunk when the browser uses the numeric loopback form
    rather than "localhost". Symptom: the shell renders and no data ever loads.
  * turbopack.root + outputFileTracingRoot must point at the repo root for
    packages/config/chains.json to resolve from web/. Vitest needs the same alias
    in its own config.
  * React 19's compiler lint rules (react-hooks/set-state-in-effect and
    react-hooks/purity) flagged three real anti-patterns: two mount-time effects
    that should have been lazy state initialisers, and Date.now() during render.
    All three were fixed rather than suppressed, and fixing the third produced
    D-16's useChainTime().
  * anvil predeploys nothing at the canonical Multicall3 address, so chains.json
    leaves multicall3 null for 31337 and wagmi falls back to individual eth_calls
    locally. Fine for development; the public chains have it.
  * npm run devchain requires a node already running (npm run anvil). Having the
    script spawn anvil itself was flaky and not worth the complexity.
